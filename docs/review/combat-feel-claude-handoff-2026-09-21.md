# Claude 인계 — CL9 전투·조작감 검증 및 개선

작성: 2026-09-21 · 프로젝트: `D:/Work/unreal/CL9` · UE 5.8

## 1. 요청

CL9의 **기본 전투와 조작감**을 먼저 검증하고 개선해 달라. 사용자는 실제 플레이가 엉성하고 재미없다고 느낀다. 주문·파밍·요리·성장 등 큰 시스템을 추가하는 방향이 아니라, 프라이팬 하나와 닭 한 마리로도 **다가가기 → 때리기 → 적 반응 → 피하기 → 다시 때리기**가 손에 붙도록 만드는 것이 목적이다.

사용자 표현: “전투? 조작감부터 좀 재미를 잡아야 될 것 같아. 시스템 말고. 뭔가 엉성하게 플레이하는 느낌이야.”

아래는 Codex의 조사 결과다. **게임 소스·에셋 수정과 비교 플레이는 아직 하지 않았다.** 확인된 사실을 재확인하고, 가설을 재현한 뒤 한 항목씩 개선해 달라. 모든 후보를 일괄 적용하라는 지시가 아니다.

## 2. 어떻게 분석했는가

### CL9 — 현재 소스와 실제 로드 에셋

- 공격 입력·판정·히트스톱·적 경직/넉백의 C++ 경로를 읽었다.
- `Tools/Unreal/run_python.py`의 Unreal Python Remote Execution으로 실행 중인 에디터에 연결했다. **MCP는 사용하지 않았다.**
- 에디터에 로드된 ItemTable·MonsterTable·CL9Rules와 공격 애니메이션 길이를 읽었다. 문서 초안이나 C++ 기본값만으로 실제 밸런스를 판단하지 않았다.
- 에셋을 변경하거나 저장하지 않았다. 로드된 게임 DLL과 작업 트리 소스의 일치 여부는 미확인이다.

### Lethal Company — 설치본 DLL 직접 디컴파일

```text
C:/Program Files (x86)/Steam/steamapps/common/Lethal Company/
  Lethal Company_Data/Managed/Assembly-CSharp.dll
```

직접 확인한 클래스:

| 클래스 | 확인한 내용 |
|---|---|
| Shovel | 준비·방출·명중·회복 시간, 판정 형태, 타격음·표면 반응 |
| GrabbableObject | 로컬 아이템 사용과 RPC 호출 순서 |
| GameNetcodeStuff.PlayerControllerB | 누름/뗌 입력, 이동·질주 코드 |

### R.E.P.O. — 설치본 DLL의 근접 무기 직접 분석

```text
D:/SteamLibrary/steamapps/common/REPO/REPO_Data/Managed/Assembly-CSharp.dll
```

`ItemMelee`를 직접 디컴파일해 움직임에 따른 공격 감지, 스윙 소리, 타격·표면 충돌·정지/반동 경로를 확인했다. 운반의 스프링·댐퍼는 기존 저장소 분석 문서를 참고했으며 이번에 관련 클래스 전체를 재분석하지 않았다.

**참고 게임의 코드 상수, 직렬화 필드 기본값, 실제 에셋값은 구별해야 한다.** 이번 리썰·R.E.P.O. 분석에서는 무기 프리팹의 실값을 새로 추출하지 않았다. 설치본이 최신 버전이라는 주장도 하지 않는다.

### 하지 못한 검증

CL9 조회 당시 PIE 월드는 없었다. 저장소 잠금 명령이 다음 이유로 거부됐다.

```text
py -3 .claude/hooks/cl9_lock.py acquire pie
훅 비활성 — 이 세션에서는 잠금을 잡을 수 없다. 세션을 재시작하라(훅은 세션 시작 때 실린다).
```

규약은 `docs/workflow/sessions.md`의 잠금 절이다. 잠금을 우회하지 않았다. 따라서 실제 입력 재현, 영상 촬영, 넉백 거리 측정, 호스트/클라이언트 비교는 미수행이다. 참고 게임도 실행해 비교 플레이하지 않았다.

**이 문서는 구조·실제 설정값을 근거로 한 원인 후보 분석이다. “재미가 검증됐다”, “수정하면 반드시 재미있어진다”는 결론이 아니다.**

## 3. CL9에서 확인한 사실과 가설

값은 2026-09-21 조회 시점이다. 작업 진행에 따라 달라졌을 수 있으므로 재확인한다.

### A. 일반 타격의 넉백이 교전 연결을 끊을 가능성 — 최우선

| 실제 로드값 | 값 |
|---|---:|
| 프라이팬 HitDamage / HitStun | 2 / Push |
| 닭 HP | 3~4 |
| 동물 5종 모두 PushKnockback | 1560cm |
| 동물 5종 모두 PushStun | 0.8초 |

`CL9Monster.cpp`의 `OnStrike`는 피해 후 살아 있는 적에 `OnShove`를 적용한다. 넉백 속도는 거리/시간, Stun 상태에서 일정 속도로 수평 이동하며 벽에 막히면 종료한다. 별도 감속은 없다.

- **확인:** 설정상 속도 1950cm/s, 장애물 없는 조건에서 약 15.6m를 밀도록 구성돼 있다. 실제 15.6m 이동을 측정한 것은 아니다.
- **가설:** 두 대면 죽는 닭이 첫 타격 후 멀리 미끄러져 다음 타격까지의 연결이 끊긴다. 좁은 방과 넓은 곳의 차이도 커질 수 있다.
- **후보:** 일반 넉백만 80~150cm 범위로 줄인 버전과 기준 버전을 비교한다. 제안 범위는 참고 게임에서 추출한 값이나 확정 밸런스가 아니다. 사망 발사는 별도로 다룬다.

### B. 공격 회복 중 재입력이 예약 없이 사라짐

`CL9Character.cpp`의 `Server_UseStart_Implementation`은 준비 시작, `Server_UseRelease_Implementation`은 준비 취소 후 `HostSwing` 호출이다. 누르고 있는 시간에 따라 피해가 달라지지 않는다.

- **확인:** `HostSwing`은 이전 시작 후 0.6초 이내면 return하며 요청을 예약하지 않는다.
- **확인:** 실제 Swing/FPSwing 클립 길이는 약 0.4667초. 헛스윙 기준으로 재공격 제한이 클립보다 약 0.1333초 길다. 화면 복귀 시점은 ABP 블렌드까지 측정해야 한다.
- **가설:** 끝났다고 느끼는 순간 다음 입력이 무시돼 조작이 끊길 수 있다.
- **후보:** 실제 입력 유실과 회복의 시각적 가독성을 먼저 측정한다. 필요하면 회복 마지막 100~150ms에 요청 하나만 예약하는 버전과 비교한다. 교체·놓기·사망·행동 불능 시 취소하고 여러 공격을 쌓지 않는다.

**중요한 보정:** 리썰 삽에도 다음 공격 예약 큐는 없다. 입력 버퍼는 CL9용 실험이지 리썰 복원이나 필수 정답이 아니다. 뗄 때 공격한다는 사실 자체도 버그가 아니다.

### C. 보이는 팬과 타격 판정이 서로 다른 팔을 따름

`CL9Item.cpp`의 `UpdateFirstPersonView`는 보이는 팬을 카메라 자식 1인칭 팔에 붙인다. `GetSwingHitSphere`는 전신 손을 따르는 루트 SphereComponent에서 판정 중심을 계산한다.

| 실제 CL9Rules | 값 |
|---|---:|
| SwingHitStart / SwingHitEnd | 0.05 / 0.25초 |
| SwingHitScale | 2.2 |
| HitStopTime | 0.08초 |

- **확인:** 표시와 판정이 다른 클립·좌표계를 사용하며 메시 경계구 반경을 2.2배로 확대한다.
- **미확인:** 실제 두 궤적의 오차량과 그 때문에 발생하는 명중/실패. 별도 팔을 쓴다는 사실만으로 오류를 확정하지 않는다.
- **검증:** 같은 거리에서 정면·아래 조준을 반복하고 보이는 팬과 서버 판정 구를 함께 기록한다. 반경을 더 키우기 전에 중심·방향·시점을 확인한다.

### D. 환경을 때렸을 때의 반응이 공격 경로에 없음

`HostTickSwingHit`는 WorldStatic·Pawn을 제외한 질의를 만들고 살아 있는 몬스터만 처리한다. 읽은 경로에 벽/바닥의 표면 타격 반응이나 대상까지의 별도 가림 검사는 없다.

- **가설:** 벽에 닿아도 허공과 비슷해 보여 도구가 공간에 존재하는 감각이 약할 수 있다.
- **검증:** 허공/벽/몬스터를 각각 때려 소리·움직임·반응을 비교한다. 벽 너머 공격 가능 여부도 재현 확인한다. 현재 벽 너머 명중을 실제로 관찰한 것은 아니다.
- **후보:** 접촉이 확인된 표면에 최소한의 타격 반응을 추가해 비교한다. 카메라 흔들림 증폭만으로 해결하지 않는다.

### E. 참여 클라이언트의 공격 시작 반응

`UseStartInput/UseEndInput`는 서버 RPC를 호출한다. 준비/공격 시작 시각은 서버에서 기록·복제되며 읽은 경로에서 로컬 공격 시작 예측을 찾지 못했다.

참여 클라이언트가 호스트보다 늦게 반응할 가능성이 있지만 실제 지연량은 미측정이다. **호스트 혼자서 느끼는 엉성함을 이 문제로 설명하면 안 된다.** 로컬 기본 감각을 확인한 뒤 2인 테스트로 다룬다.

## 4. 참고 게임에서 실제로 배울 점

### 리썰: 더 빠른 공격보다 예측 가능한 준비·조준·접촉

설치본 Shovel 코드의 순서는 다음과 같다.

```text
누름 → 즉시 준비 상태·소리
     → 최소 0.35초 대기(일찍 떼어도 생략 불가)
     → 뗌 확인 후 스윙
     → 0.13초 + 프레임 끝 대기 후 판정
     → 0.3초 후 공격 중 플래그 해제
```

짧은 탭의 명중은 이론상 누름 후 약 0.48초 이후, 다음 준비 가능 시점은 약 0.78초 이후다. 코드 대기 시간의 합이지 영상 측정값이 아니다. 오래 준비했다고 피해가 커지는 경로는 없다. 공격 중에는 새 코루틴을 시작하지 않는다.

판정은 삽 메시 궤적이 아니라 카메라에서 오른쪽 기준 -0.35m 지점을 원점으로 하는 **반경 0.8m, 전방 이동 거리 1.5m의 SphereCastAll**이다. 1.5m는 구 중심 이동 거리이며 전체 도달 범위를 뜻하지 않는다. 결과를 거리순으로 처리하고 타격 대상까지 가림 검사도 한다(맞은 점이 영벡터인 경우 해당 Linecast 조건 예외).

환경 표면도 인식해 태그에 맞는 타격음을 고른다. 로컬 `UseItemOnClient`는 RPC 응답을 기다리지 않고 `ItemActivate`를 실행하며 준비 동작과 소리를 시작한다.

**CL9에 대한 해석:** 리썰보다 무조건 더 빠르게 휘두르는 것이 목표가 아니다. 준비/회복을 읽을 수 있는지, 보는 방향으로 납득되게 맞는지, 허공·표면·적을 구분할 수 있는지가 중요하다. 리썰의 판정 권위나 수치를 그대로 복사하라는 뜻은 아니다.

### R.E.P.O.: 큰 밀침보다 움직임·접촉·저항의 연결

이번에 직접 확인한 `ItemMelee`:

- 이전 표본과 현재 Swing Point의 변위로 Swinging 상태를 감지한다. 표본은 약 0.1초 간격으로 갱신된다. 문턱값을 그대로 속도 단위로 해석하면 안 된다.
- 이동·회전 속도 등에 따라 스윙 소리의 피치와 볼륨이 변한다.
- 일반 타격과 GroundHit의 소리·파티클을 구분한다.
- 잡은 비키네마틱 무기의 선속도·각속도 초기화와 조건부 FreezeForces 경로가 있다.
- 물체 접촉 시 접촉점 소리·파티클과 정지/반동 경로가 있다.

`hitFreeze=0.2`는 코드 기본값만 확인했으며 무기 프리팹 실값이 아니다.

**CL9에 대한 해석:** 고정 스윙 뒤 적을 멀리 밀어내는 것으로 같은 물리 손맛이 생기지는 않는다. R.E.P.O. 전체 물리 시스템을 도입하기보다, 기존 팬의 접촉과 적 반응이 연결되는지 먼저 검증한다.

### 이동 감각은 후속 범위로 분리

리썰은 질주 배수를 점진적으로 올리고 해제 때 더 빠르게 낮추며, 입력 방향 변화율에 무게가 관여한다. CL9 커스텀 이동 코드는 걷기/질주 상한을 상태로 고른다. **UE CMC의 가속·제동이 있으므로 실제 이동이 즉시 바뀐다고 단정하지 않는다.** 전투 실험과 이동 튜닝을 한 번에 섞지 않는다.

## 5. 실행 순서와 산출물

1. `CLAUDE.md`, `docs/workflow/sessions.md`, 관련 규약 및 현재 변경사항을 확인한다. 미커밋 소스·에셋 변경이 다수 있으므로 기존 작업을 덮어쓰거나 되돌리지 않는다.
2. 정상 잠금 절차와 실행 DLL 상태를 확인하고 현재 에셋값을 다시 읽는다. 이 문서의 과거 스냅샷을 그대로 현재값으로 간주하지 않는다.
3. 프라이팬과 닭 하나로 기준 플레이를 기록한다. 넓은 곳/벽 근처, 정면/아래 조준, 탭/홀드/회복 중 재입력을 포함한다.
4. 넉백을 단독 비교한다. 표면 반응과 화면-판정 정합성도 확인하고, 입증된 문제부터 작은 변경으로 비교한다.
5. 입력 버퍼는 회복 피드백과 입력 유실 결과에 따라 시험한다. 누름 즉발 변경과 동시에 섞지 않는다.
6. 채택한 로컬 개선을 함께 확인한 뒤 호스트/참여 클라이언트를 비교한다.

기록할 것:

| 항목 | 기록 |
|---|---|
| 공격 시간 | 누름·뗌·준비 표시·공격 시작·명중·경직 종료·다음 공격 시작 |
| 넉백 | 이동 거리·지속시간·벽 충돌 여부 |
| 입력 | 수락·예약·거절 여부와 당시 회복 상태 |
| 판정 | 거리·조준각·보이는 접촉·서버 명중 시점 |
| 실행 조건 | 호스트/참여 클라, 프레임률, 빌드 및 사용값 |
| 체감 | 동일 조건 기준/수정 버전에 대한 사용자 비교 평가 |

실제 마우스 입력과 RPC 직접 호출 검증을 구분한다. 컴파일·자동 테스트 통과를 재미 검증으로 보고하지 않는다. 변경 전후 값, 재현 결과, 채택/보류 이유, 남은 가설을 짧은 보고서로 남긴다.

성공 기준은 **한 대 친 뒤 다음 행동이 이어지고, 입력과 명중이 납득되며, 사용자가 기존보다 손에 붙는다고 느끼는 것**이다. 새 몬스터·아이템·진행 시스템 추가로 범위를 넓히지 않는다.
