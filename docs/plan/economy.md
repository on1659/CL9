## 화폐는 이더다

> **2026-10-12 이름 바꿈(사용자, [../goal/loop-7f-out-game-currency.md](../goal/loop-7f-out-game-currency.md))**: 판 안 화폐의 **화면 이름은 "코인"**이고,
> **"이더"는 이제 아래 "외부 재화"(개인 소유 바깥 재화)의 이름**이다. 이 문서와 다른 기획·시스템 문서의 옛 "이더"(판 돈)는 코인으로 읽는다 —
> 이력 문서라 본문은 고치지 않는다. 코드 이름(`SharedMoney`·`PeriodIncome`, 로그의 "ether")도 그대로다.

**단위는 이더.** 1이더 · 2이더처럼 센다. 정수이고 소수점을 쓰지 않는다.

가격이 붙는 곳은 전부 이더다 — 아이템 값 · 몬스터 값 · 주문 보상 · 목표액 · 장비 가격.

### 외부 재화 — 이더와 다른 층 (2026-10-11 사용자, 명세 [../goal/loop-rework.md](../goal/loop-rework.md))
- **쓰는 곳(2026-10-12, 7k)**: 회사의 옷장에서 치장 스킨을 산다(대역 — 옷 색만 바꾼 작업복 셋, 초안 20·30·60 이더). 스킨은 몸 전체를 바꾸는 방식이고 모델이 들어오면 `SkinTable` 에 행만 더한다([../goal/loop-7k-skins.md](../goal/loop-7k-skins.md)).

이더는 **판에 묶인 호스트의 것**이다. 그 위에 **플레이어 개인(Steam 계정) 소유의 외부 재화**가 하나 더 생긴다.

- 판이 끝나도, 판이 죽어도 남는다. 저장은 판 세이브가 아니라 개인 저장소다.
- **치장(스킨 등)만 산다. 게임 밸런스에 영향이 없다** — "영구 성장은 범위 밖"이라는 원칙은 그대로다.
- 존재 이유는 **임포스터**다. 협동만 하면 손해 볼 게 없으니 배신할 동기가 없고, 외부 재화가 그 동기다 —
  임포스터가 성공하면 그 판의 이더는 못 벌어도 외부 재화를 받고, 임포스터를 처치한 사람도 받는다.
- 어디서 버나(판 수입 비율·정산 성공·처치 보상만…)·액수·상점 위치는 **미결** — 그 명세의 미결 목록.
- **2026-10-12 구현(7f)**: 이름은 **이더**. 판 끝에 **살아서 트럭으로 돌아온 사람**이 그 **판 수입(코인)에 비례**해 받는다 —
  `CL9Rules.WalletIncomeRate`(초안 0.01 = 100 코인당 1 이더 → **2026-10-17 0.08** — 코인 눈금 1/8 과 함께 올려 계란 한 개 ≈ 이더 하나는 그대로, 사용자 "그래야 더 열심히 한다"). 임포스터 성공·처치 보상(7g)은 **이보다 커야** 한다.
  저장은 각자 기계의 파일(`CL9Wallet`)이고 새벽 화면·타이틀에 보인다.

### 딸려오는 것 — 재료를 직접 쓰지 않는다

돈이 생기면 물건과 장비 사이에 한 단계가 늘어난다.

```
전:  계란 2개  →  프라이팬
후:  계란      →  팔아서 이더  →  프라이팬
```

그래서 "재료 1개 = 용도 3개"의 **모으면** 항목이 "재료를 모아 바꾼다"가 아니라
"팔아서 산다"가 된다. 세 갈래가 사라지는 건 아니지만 — 먹을지, 팔지, 주문에 넘길지 —
장비가 재료와 직접 이어지지는 않는다.

## 이더의 흐름

```
원정에서 주움  →  요리  →  납품  →  이더  →  장비 구매
                            ↑                ↑
                        여기서 생기고      여기로 나간다
```

**들어오는 곳**
- 주문 납품 보상 (`order.md`의 `RewardMin`/`RewardMax`)
- 주문 외 물건을 그냥 파는 것 — 판매가는 아래 가격식 그대로다. 대신 주문 보상을 재료 값 합의
  2~3배(초안)로 잡아 **주문이 항상 주 수입**이 되게 한다 — 남는 재료는 쓰레기가 안 되고,
  주문서는 보너스로 격하되지 않는다

**나가는 곳**
- 장비 구매 (`equipment.md`의 `Price`)
- 주문 위약금 — 마감을 놓친 주문은 보상의 일정 비율을 뺀다 ([data/order.md](data/order.md)).
  차감 후 잔액은 0 아래로 내려가지 않는다 (채무 불가와 동일한 하한)
- 전멸 패널티 — 전원이 죽으면 게임 오버 대신 그 판만 끝나고, **누적 이더의 30%를 깎는다**(2026-10-11 사용자, 30%는 2026-10-12 —
  데이터 셀로 두어 나중에 바꾼다, [../goal/loop-rework.md](../goal/loop-rework.md))
- 그 외는 없다 — 수리비·유지비 없음 (현재 설계)

**남는 이더는 다음 날로 넘어간다.** 누적 자금은 진행 상태이지 에셋이 아니다
([data/progression.md](data/progression.md)).

## 가격이 계산되는 식

```
최종 가격  =  [ValueMin, ValueMax] 굴림  ×  목적지 배율  ×  일자 배율
```

| 항 | 어디 | 컬럼 |
|---|---|---|
| 개체 기본값 | [data/item/common.md](data/item/common.md) · [data/monster/common.md](data/monster/common.md) | `ValueMin` / `ValueMax` |
| 목적지 배율 | [data/site.md](data/site.md) | `ValueRate` |
| 일자 배율 | [data/progression.md](data/progression.md) | `ValueCurve` |

**개체마다 굴린다.** 같은 계란이라도 80이거나 120이다. `min = max`면 고정값이다.

**두 배율을 동시에 만지지 않는 게 좋다** — 목적지 1.5 × 일자 1.4 = 2.1이 되어 최종값 예측이
어려워진다. 한쪽을 평평하게 두고 다른 쪽만 조정한다.

**눈금은 계란이 잡는다** — 성한 계란(배율 1.0 기준)이 **10~15코인**이다(2026-10-17 사용자 "첫 목표는 100" — 옛 80~120 의 1/8).
나머지 가격은 전부 여기서 역산한다 — 옛값 ÷ 8 을 정수로 반올림하고, 주문 보상은 5 단위로 맞춘다.
옛 눈금 80~120 은 정수 화폐에서 굴림과 배율(×0.8~×1.4)이 반올림에 먹히지 않게 키운 것이었는데, 첫 정산 목표 800 이
숫자로 너무 커 보여 되돌렸다. 배율이 계란 10~15 에 걸릴 때 생기는 ±0.5 코인(약 4%)의 반올림 오차는 받아들인다.

## 난이도가 오르는 축

일자 곡선이 무엇을 움직이는지. 컬럼은 [data/progression.md](data/progression.md)에 있다.

| 축 | 움직이면 | 초안 |
|---|---|---|
| 몬스터 수 | 통로가 막힌다. 제일 직관적인 난이도 | 오른다 |
| 위험도 | 같은 마릿수로 압박이 오른다 (추격 예산·발각 속도) | 오른다 |
| 재료 수 | **난이도가 아니라 보상이 오른다** | 평평 |
| 가격 | 인플레이션. 목표액과 짝 | 오른다 |
| 목표액 | 벌어야 하는 양 | 오른다 |
| 밤 길이 | **줄이면 압박이 아니라 짜증이 된다** | 평평 |

**재료 수와 밤 길이를 평평하게 두는 게 초안이다.** 목표액만 올리고 나머지를 두면 "같은 재료로
더 벌어야 한다"가 되어 압박이 생긴다. 재료를 같이 늘리면 그 압박이 사라진다.

밤 안에서의 압박은 정전 시계가 이미 담당한다 — 그 위에 시계를 하나 더 얹으면 둘 다 안 읽힌다.

## 공급 대비 목표 (2026-10-20)

정산 목표는 맵이 주는 양에서 거꾸로 정한다. 둘을 따로 정하면 이번처럼 목표가 공급의 8%로 떨어져도 아무도 모른다
([C:\Work\CL9\docs\goal\henhouse-supply-quota.md](C:\Work\CL9\docs\goal\henhouse-supply-quota.md)).

```
공급 S  = 정산 기간(세 판)의 날재료 판매값 합 = Σ(재료 개수 평균 × 값 평균 × 재료 수 곡선) × ValueCurve(지금 에셋은 빈 곡선 = 1.0)
목표 Q  = S × 비율          비율: 첫 정산 0.45 → 6일차 0.6 → 9일차 0.75 → 12일차 0.9
```

| 정산일 | 양계장 S (날재료) | 비율 | 목표 `QuotaCurve` | 주문만(2개/판, 평균 120) |
|---|---|---|---|---|
| 3일차 | 427 × 3 ≈ 1,280 | 0.45 | **600** | 720 |
| 6일차 | ≈ 1,280 | 0.6 | **775** | 720 |
| 9일차 | ≈ 1,280 | 0.75 | **950** | 720 |
| 12일차 | ≈ 1,280 | 0.9 | **1,150** | 720 |

`CL9Progression.ValueCurve` 는 비어 있어(2026-10-20 에셋에서 읽음) 값 배율이 늘 1.0 이다 — 그래서 S 가 정산마다 같다.
30일차 키 2,290 까지 정산마다 약 190씩 계속 오른다.

- 첫 정산은 "매 판 주문 두 개를 해내면 별 1개"다. 별 3개(200%)는 날재료 공급의 94%여서 요리해 팔거나 주문을 더 해야 닿는다.
- 뒤 정산은 주문만으로 모자라고, 12일차에 양계장 날재료 공급의 0.9배가 된다. 대농장(공급 ≈ 2.4배)·돼지 농장(≈ 2배)에서는 같은 목표가 30~45%라
  큰 목적지로 갈 이유가 된다. 리썰도 첫 쿼터(300)가 첫 달 세 날 공급의 약 30%이고, 쿼터가 달성 횟수의 제곱으로 오른다
  ([C:\Work\CL9\docs\reference\lethal\lethal-run.md](C:\Work\CL9\docs\reference\lethal\lethal-run.md) "쿼터 갱신 공식").
- 주문 보상은 `ValueCurve`를 받지 않는다(`ACL9GameMode` 수락 때 `RewardMin~Max` 그대로) — 그래서 뒤로 갈수록 주문만으로는 모자라다.
- 재료 개수·구역 몫·목표를 바꿀 때는 이 표를 같이 다시 계산한다.

## 지켜야 하는 부등식

수치를 바꿀 때 이게 깨지면 게임이 조용히 망가진다. **로드할 때 검사하고 깨지면 로그에 찍는다.**

| # | 관계 | 깨지면 |
|---|---|---|
| A1 | 지친 빈손 속도 > **잡는(Catch) 몬스터**의 추격 속도 | 짐을 다 버려도 못 도망친다 (경보꾼 거위는 대상 아님) |
| A2 | 질주 예금 > 시야 반경 | 직선 복도에서 시야를 못 끊는다 |
| A4 | **잡는(Catch) 몬스터**의 추격 < 운반 질주 | 잡힘이 확정된다 (A1과 같은 한정 — 경보꾼 거위는 대상 아님) |
| A5 | `PounceRadius + WalkSpeed × PounceWindup` > `CatchRadius + PounceLunge` **그리고** `PounceRadius ≥ CatchRadius` — 잡기 예고가 켜진 종(`CatchRadius > 0 ∧ PounceWindup > 0`)마다 | 예고를 보고 걸어서 물러나도 잡힌다 — 사용자 결정 D2(2026-09-19 "걷기로 물러나도 피한다") 위반. 둘째 식이 깨지면 예고 없이 잡히는 거리가 생긴다 (`CatchRadius 0` 또는 `PounceWindup 0`인 종은 "Pounce 없음"으로 통과) |
| A6 | `ExecuteAnchorDistance ≥ Radius + CapsuleRadius(39)` — 스토커 종(`ExecuteRadius > 0` — 너구리)마다 | 처형 앵커가 피해자 캡슐과 겹쳐 순간이동한 너구리가 피해자 몸에 박힌다(규칙 3 "캡슐이 기준" 위반 — D1). 로드 검사와 같은 식. 잡히면 처형하는 종(돼지)은 텔레포트가 없어 대상 아님 |
| A7 | `StalkRetreatRadius > 0 ⇒ RetreatSpeed > 0` | 들킨 너구리가 물러나야 하는데 속도가 0 이라 제자리에 굳는다 — 로드 검사와 같은 식 |
| — | `bExecuteOnCatch ⇒ ExecuteDuration > 0` — 잡히면 처형하는 종(돼지) | 잡는 순간 처형에 들어갔는데 지속이 0 이라 카메라가 넘어가자마자 죽는다(처형이 안 보인다) — 로드 검사와 같은 식 |
| — | 처형 회피 산수(판정, 아래 파생값 — 스토커 종만): `180 − StalkGazeHalfAngle > ExecuteBehindAngle` **그리고** `ExecuteUnseenTime > 복제 지연 0.1` | 첫째가 깨지면 피해자가 보고 있는 너구리가 "등 뒤"로도 판정되어 시선으로 막을 수 없는 처형이 생긴다. 둘째가 깨지면 돌아본 순간 복제가 닿기 전에 처형이 들어온다(D5 — 지연 ~100ms 수용) |
| — | 탈진 운반 < **잡는 몬스터**의 추격 | 운반의 위험이 사라진다 |
| — | `KillCooldown` = `RageTime` | 한 손잡이가 둘로 갈라진다 |

| **시선·등 뒤 간격** (회피 산수 1) | `180 − StalkGazeHalfAngle − ExecuteBehindAngle` — 피해자 시야 원뿔 가장자리와 등 뒤 원뿔 가장자리 사이 각. 양수여야 "보고 있으면 등 뒤가 아니다" | 너구리 180 − 55 − 60 = **+65°** |
| **처형 반응 여유** (회피 산수 2) | `ExecuteUnseenTime − 복제 지연 0.1 − 180° 회전 0.3` — 마지막으로 돌아본 뒤 다시 돌아보기까지 쓸 수 있는 시간. 회전 0.3은 마우스 반바퀴 추정(표에 없는 값 — 참고) | 너구리 3.0 − 0.1 − 0.3 = **+2.6초** |
| **정지 타깃 처형 시점** (참고) | `max((SightIn − ExecuteAnchorDistance) / StalkSpeed, ExecuteUnseenTime)` — Stalk 진입부터 Execute 진입까지, 안 돌아보는 혼자 | 너구리 max(270/450 = 0.6, 3.0) = **3.0초** → 죽음 +2.0 = 5.0초 (Run 2 초안 `ExecuteDuration`, 2026-09-21) |
| **스토킹 좁힘 속도** (참고) | `StalkSpeed − WalkSpeed` — 걷는 사람 등 뒤에 붙는 속도(양수여야 걷는 사람도 잡는다 — 사용자 확정 450) · 달리기로 벌어지는 속도 `RunSpeed − StalkSpeed` | 너구리 450 − 396 = **+54cm/s**(390 → 120 까지 270cm = 걷는 타깃 5.0초) · 654 − 450 = **204cm/s** 벌어짐 |
| **잡히면 처형 — 잡히기까지** (참고, 돼지) | `(SightIn − PounceRadius) / ChaseSpeed + PounceWindup` — Chase 진입부터 덮침(= Execute 진입)까지, 안 움직이는 혼자. 걷는 사람은 `ChaseSpeed − WalkSpeed` = 0 이라 못 좁힌다 | 돼지 (480 − 146)/396 + 0.8 = **1.6초** → 죽음 +2.0 = 3.6초 (Run 2 초안 `ExecuteDuration`, 2026-09-21) · 수레(297)는 99cm/s 로 좁혀 약 2초마다 재예고 |

**A1·A2·A4는 캐릭터 행마다 검사한다.** 몸 수치가 캐릭터 표에 있어서, 값을 갈랐을 때 부등식도
캐릭터마다 달라지기 때문이다 ([data/character.md](data/character.md)). A5도 `WalkSpeed`가 들어가
같고, A6 도 `CapsuleRadius`가 들어가 같다. 에디터 없는 쌍둥이 검사는 `py -3 Tools/Balance/check_inequalities.py`다.

### 스토킹과 처형 — 너구리·돼지 관찰 (2026-09-20 저녁, 전부 초안)

처형(즉사)은 두 종에 있고 들어가는 길이 다르다(사용자 결정 2026-09-20 저녁): **너구리 = 몰래 뒤에서
처형(스토커)**, **돼지 = 잡히면 무조건 처형**.

**너구리** ([data/monster/raccoon.md](data/monster/raccoon.md))는 잡는 종이면서 스토커다. 격분 뒤의 추격·예고는
A1·A5 로 닭과 같은 약속을 지키고(`ChaseSpeed` 462, A1 여유 +44.6), 처형은 위 회피 산수 두 줄이 지킨다.
스토킹의 긴장은 사용자 확정값 셋이 만든다 — `StalkSpeed` **450 > 걷기 396**(걸어도 54cm/s 로 따라붙는다 —
390 에서 발견된 걷는 사람은 5.0초 뒤 등 뒤에 닿는다; **달리기 654 로만 뗀다**, 204cm/s 씩 벌어져 1초 남짓에
`DeaggroRadius` 510 밖), `StalkStareAnger` **6**(흘깃은 안전, 노려보기는 6초까지 방패), `SleepTime` **0**(밤 내내
돈다). `ExecuteUnseenTime` 3.0 은 그대로(혼자면 3초에 한 번 돌아봐야 한다) — 450 이 이미 걷는 사람을
잡게 했으니 시계까지 줄이면 이중 벌이다.

**돼지** ([data/monster/pig.md](data/monster/pig.md))는 닭과 같은 추격·예고·덮침 끝에 **잡히는 순간이 처형**이다
(`bExecuteOnCatch`, 텔레포트 없음). 잡히면 즉사라 추격 속도를 **걷기와 같은 396** 으로 내렸다(옛 480 은 걷는
사람을 84cm/s 로 좁혀 "걷는 사람이 무조건 죽는 종"이 된다) — 돼지는 걷는 사람을 못 잡고 **멈춘·막힌·수레 끄는
사람**을 잡는다. 예고 0.8 은 A5 여유 +253 으로 잡는 종 중 제일 두껍고, 잡히기까지는 정지한 혼자 기준 1.6초(파생값 표).

PIE C-처형-너구리·C-처형-돼지에서 볼 것: 스토킹이 읽히는 거리·속도(450 이 발소리 없이 붙으면 예고 없는
즉사다), 6초 응시가 과한 방패인가, 처형 성공률(2인에서 동료가 지켜보는 대응이 통하는가), 걷기 속도 돼지가
"느리지만 무서운"으로 읽히는가 "무해한"으로 읽히는가. 관찰 뒤 조정 후보(어느 쪽으로 틀지는 관찰이 정한다):

| 관찰 | 후보 | 왜 |
|---|---|---|
| 너구리 처형이 예고 없이 온다 — 읽히지 않는다 | `SightIn` 390 → **600**, `StalkRetreatRadius` 250 → **350** | 더 멀리서 스토킹을 시작하고(걷는 타깃 5.0 → 8.9초) 들키면 더 멀리 물러난다. A2 3924 > 600 × 1.3 = 780 그대로 통과. `StalkSpeed` 450 은 사용자 확정 — 속도로 풀지 않는다 |

### 잡기 예고와 넘어짐 무적 — 다마리 난이도 관찰 (2026-09-20)

두 결정이 같은 날 들어왔다: 잡기는 예고(`Pounce`) 뒤에 오고(사용자 D1·D2), **넘어져 있는 동안은 맞지
않는다**(사용자 결정 2026-09-20 — `OnDamage`의 `IsKnockedDown()` 게이트, 치트 포함; 몬스터도 넘어진
타깃엔 예고·잡기를 시작하지 않고 옆에서 기다린다). 그 결과 한 사람이 맞는 최소 간격이 값으로 정해진다:

| 파생값 | 식 | 현재 값 |
|---|---|---|
| **연타 최소 간격** | `KnockdownTime + PounceWindup` — 일어나는 순간 옆에 있던 다른 몬스터가 곧바로 예고해 덮치는 경우 | 1.5 + 0.6 = **2.1초** |
| **서서 맞아 죽는 시간** | `(HpMax − 1) × 연타 최소 간격 + PounceWindup` — 몬스터 두 마리 이상이 붙어 있고 사람이 제자리에 서 있을 때 | 2 × 2.1 + 0.6 = **4.8초** (HP 3) |

전에는 닭 열 마리가 넘어진 1.5초 안에 차례로 잡아 HP 3이 한 번에 사라졌다. 이제 마릿수는 **연타를
못 만든다** — 열 마리에서도 간격은 2.1초다. 그래서 다마리의 긴장은 세 곳에서만 나온다:

1. **재예고** — 일어나면 옆의 몬스터가 즉시(0cm에서) 예고한다. 걸어서 물러나면 헛침(0cm 여유 닭 44 ·
   너구리 24)이라 "일어나자마자 걷는다"가 생존 규칙이 된다.
2. **마릿수** — 예고가 여러 방향에서 겹치면 물러날 방향이 좁아진다. 옆걸음도 헛침이라(닭 271 > 194)
   방향 하나만 비어 있어도 산다 — 완전히 둘러싸여야 잡힌다.
3. **`PounceMissCooldown`** — 헛친 몬스터가 다시 예고하기까지. 너구리는 걷는 사람도 1.6초마다 다시
   예고해 시달리게 한다(닭은 못 따라붙는다).

PIE `cl9.addmonster chicken 10`에서 볼 것: 연타 없음(로그 "hit by … while knocked down — ignored",
`HurtEvent.Seq` 불변), 재예고 간격이 2.1초 부근인지, 열 마리 예고가 겹칠 때 물러날 방향이 남는지.
관찰 뒤 조정 후보(어느 쪽으로 틀지는 관찰이 정한다):

| 관찰 | 후보 | 왜 |
|---|---|---|
| 열 마리가 순해서 긴장이 없다 | `PounceMissCooldown` 0.6 → **0.3** | 재예고 주기 1.2 → 0.9초. `KillCooldown`엔 안 닿는다 |
| 둘러싸여도 너무 쉽게 빠진다 | `PounceWindup` 0.6 → **0.5** | 이상적 후퇴 0.16 + 반응 0.25 = 0.41 < 0.5로 D2는 지키되 여유 0.19 → 0.09. 0.45 아래로는 내리지 않는다(반응 시간이 먹힌다) |
| 일어나자마자 또 잡혀 답답하다 | `KnockdownTime` 1.5 → **2.0**([data/character.md](data/character.md) — character 공유 파일) | 연타 간격 2.1 → 2.6초. `HurtLookTime + 0.6 ≤ KnockdownTime`은 그대로 통과 |
| 열 마리로도 심심하다 | 양계장 기본 8~12 → 마릿수 조정([data/site.md](data/site.md)) | 예고 방향이 늘어야 긴장이 는다 — 값이 아니라 개수 |

파동 행 `monster_pounce`([data/wave.md](data/wave.md))의 `FallbackRadius`는 판정이 아니지만
`Speed 510 × PounceWindup 0.6 = 306`으로 **링이 다 퍼지는 순간 = 덮치는 순간**에 묶었다 —
`PounceWindup`을 바꾸면 그 행도 같이 바꾼다.

값 미결은 이 문서에 없다 — 남은 것은 각 표 문서의 "미결" 절에 있다.
