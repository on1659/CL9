# 모델·리깅·애니메이션·인게임 제작 파이프라인

작성: 2026-10-12 · 개정: 2026-10-13. `$cl9-model-concept`의 범위·승인·재개 절차 정본.
기존 호출명은 유지하며, 전체 제작 요청은 **컨셉 → 3D 초안 → 짧은 동작 시험 → 모델·리그 → 애니메이션 → 게임 검수**까지 이어간다.

## 시작과 문서 소유권

```text
$cl9-model-concept 소 탈 몬스터를 컨셉부터 리깅·탈 벗기/입기·인게임 검수까지 새로 제작해줘.
$cl9-model-concept <대상> 컨셉 이미지만 만들어줘.
$cl9-model-concept <기존 제작 문서 경로>에서 저장된 단계부터 재개해줘.
```

1. [에셋 안내](README.md)·[목록](catalog.md)에서 대상의 현재 카드/인계서 하나를 찾는다. 신규 대상만 [양식](brief-template.md)을 사용한다. 단계별 병행 인계서나 `docs/model/`을 만들지 않는다.
2. 관련 기획·승인 이미지·[공통 규격](common.md)·[시각 방향](design-concept.md)을 읽고 이번 범위를 기록한다. 전체 제작에는 [제작 절차](workflow.md#animal-production)를 적용한다.
3. 현재 프로젝트와 엔진, 소비할 리그/애니메이션 경로를 확인한다. 이름이 같은 다른 체크아웃의 파일을 임의로 섞지 않는다.
4. 기존 승인 발언·대상 버전·실제 파일을 확인한다. 파일명 `approved`, 에이전트 평가, 파일 존재만으로 승인을 추정하지 않는다.

| 범위·승인·재개·완료 | 이 문서 |

| 상태 빈 양식 | [brief-template.md](brief-template.md#concept-checkpoint) |

## 범위와 완료 계약

| scope | 요청 예 | 끝나는 조건 |
|---|---|---|
| `concept_only` | 컨셉/이미지만 | 요청 이미지 제시와 적용되는 외형 검토 완료 |
| `model_only` | 외형 모델/Blender 초안까지만 | 컨셉·Blender 검토와 실제 파일/렌더, 남은 제작 인계 |
| `production` | 리깅·애니메이션·인게임까지 | 요청한 제작과 기술 QA·실제 게임 검수·영상 납품 완료 |

`requested_outputs`에 실제 요청 클립과 엔진 검수 범위를 적는다. 일반 소품에 리그/탈착/멀티플레이를 강제하지 않는다.
요청이 명확하면 재질문하지 않는다. 범위가 “모델만”이라면 불필요하게 전체 게임 시스템을 새로 구현하지 않는다.
전체 제작이 허용된 경우 초안 승인 뒤 인계서만 쓰고 멈추지 않는다. 새 AI/게임 규칙 구현이 필요하면 기존 연결로 가능한 일부터 진행하고, 부족한 기능과 추가 범위를 구체적으로 구분한다.

## 단계와 검토

| phase | 실제 작업 | 다음 단계 조건 |
|---|---|---|
| `brief` | 자료·범위·엔진 소비 경로 확인 | 목표/미정 사항을 카드에 기록 |
| `concept_work` / `concept_review` | 이미지와 탈/본체/중간 구조 설계·제시 | 적용되는 컨셉 검토 완료 |
| `blender_work` / `blender_review` | 실제 3D 초안·다각도 렌더 | 적용되는 Blender 외형 검토 완료 |
| `motion_probe` | 어려운 2~3초 접촉·통과 시험, 작은 엔진 왕복 | 핵심 구조가 작동하며 실패/미검증을 구분 |
| `model_rig` | 변형용 메시·UV·재질·최종 리그/웨이트 | 극단 포즈·외형·접촉 제어 검사 |
| `animation` | 요청 클립과 탈착 시퀀스 제작·보정 | 정상 속도 동작/접촉/전환 검수 |
| `engine_verify` | 엔진 임포트·실제 소비 경로 연결·플레이 | 요청 범위의 실행 증거와 인게임 영상 |
| `delivery` | 출력·영상·QA·재개 정보 정리 | 범위별 완료 조건 충족 |
| `complete` | 요청 범위 완료 | 미검증 항목을 완료로 올리지 않음 |

`handoff`는 구버전에서 쓰던 초안 인계 단계로 읽을 수 있으며 `production`의 종료 지점은 아니다.
`status`는 `working / awaiting_user / blocked / paused / complete`이다. 이 값은 문서 상태이며 Codex goal 상태와 별개다.
사용자 중단 요청에 `paused`, 실제 파일/도구 장애에 `blocked`와 재개 조건을 기록한다. 품질 수정 중은 `working`이다.

### 승인과 자율 진행

기본 `review_policy: concept_and_model`은 컨셉 이미지와 실제 Blender 외형의 **서로 다른 두 검토**를 유지한다.
이미 승인된 버전은 다시 묻지 않는다. 사용자가 명시적으로 검토 없이 진행하라고 하면 `user_directed`와 실제 지시를 기록하여 따르되, 미래 결과를 사용자 승인본으로 만들지 않는다.

- 특정 후보를 본 뒤 “OK/이 버전으로”는 그 후보에 적용한다. 단일 후보 대기 중의 짧은 OK도 가능하다.
- NO/조건부 수정은 피드백과 유지할 특징을 기록하고 새 후보를 보여준다. 여러 후보 중 대상이 불명확하면 그 선택만 확인한다.
- 침묵·시간 경과·일반적인 “계속”·렌더 성공·자체 QA는 사용자 승인 근거가 아니다.
- 전체 제작 요청과 외형 검토가 충족되면 기술 단계마다 허락을 다시 묻지 않고 요청 범위까지 진행한다. 내부 짧은 시험은 추가 승인 관문이 아니다.
- 승인된 실루엣/비율/캐릭터성을 크게 바꿔야 하면 변경 후보를 제시한다. 승인 외형을 유지하는 웨이트·토폴로지·접촉 보정은 파생 작업본에서 진행하며 외형 승인을 반복 요구하지 않는다.

대기 전 후보 버전·경로·제시 자료·다음 행동을 저장한다. 실제 후보를 보여주고 정확히 어떤 검토가 필요한지 설명한다.
필요한 검토 없이 의존 작업을 시작하지 않으며, 이미 허용된 독립 작업은 계속할 수 있다.

## 컨셉과 실제 3D

컨셉은 사용자가 선택한 모델과 사용 가능한 이미지 생성 도구로 만든다. 특정 모델을 자동 전환했다고 주장하지 않는다.
실루엣·비율·얼굴·색·식별 요소를 확인한다. 탈 몬스터는 평상시·본체·탈착 중간의 구조도 설계하며, 모든 동물에 닭의 긴 팔다리와 같은 얼굴을 복제하지 않는다.

보이지 않는 면과 입구 구조가 중요하면 보조 뷰/도해를 준비한다. 기준 이미지에서 크게 달라지는 뒷모습이나 분리 구조는 같은 컨셉 검토 묶음에 포함한다.
컨셉 이미지·프롬프트·입력 출처·도구 조건을 보존한다. 기본 검토 정책에서는 이미지 OK 뒤 3D를 시작한다.

3D는 직접 모델링 또는 생성 초안 후 보정을 선택한다. 생성 도구 성공을 게임용 메시·리그 완료로 해석하지 않는다.
초안은 실루엣·측면 두께·색·몸/탈 분리·입구·수납 공간·잡는 위치를 보여준다. 정밀 UV/완성 리그는 뒤에 하되, 승인 이미지의 핵심 형태를 편의상 단순 도형으로 대체하지 않는다.

**저장한 실제 .blend**에서 정면·측면·후면·사선을 렌더한다. 파일을 다시 열고 의존 텍스처와 장면 일치를 확인한다.
AI가 그린 3D풍 이미지를 모델 렌더 증거로 쓰지 않는다. 사용자 씬·다른 세션 파일은 초기화하지 않는다.
외형 검토 후 `production`은 [짧은 동작 시험과 본제작](workflow.md#animal-production)으로 계속한다.

## 저장·버전·중단 복구

### 상태 형식

기존 카드의 `concept_pipeline` 키를 유지하고 `schema_version: 2`로 확장한다. [빈 양식](brief-template.md#concept-checkpoint)을 사용한다.

- `scope`, `requested_outputs`, `review_policy`, `review_override`는 요청 범위와 실제 검토 방식/사용자 지시다.
- `concept/blender.candidate_version`, `approved_version`과 `blender.source_concept_version`은 외형 후보·승인 관계다.
- `production`은 `source_blender_version`, `candidate_version`, `manifest`, `qa`, `runtime`을 기록한다. QA 항목은 `not_run / pass / fail / not_applicable`와 증거를 사용한다.
- `runtime.level`은 `not_tested / imported / preview / gameplay_verified` 중 실제 수준이다. 단순 배치·시퀀스 반복은 `preview`다.
- `pending_review`는 `{stage, version, presented_at, evidence}`. 제시하지 않은 자료의 시각을 만들지 않는다.
- `checkpoint`는 실제 편집 파일 `{path, sha256}`. `job`은 실행 중인 작업의 도구·ID·시작 시각·명령·로그·출력 폴더다.
- `last_completed / next_action / blocker`는 끝난 사실·다음 행동·장애를 구체적으로 적는다.

날짜는 시간대가 있는 ISO 형식으로 기록한다. 후보 생성, 피드백/승인, 긴 작업 시작·종료, 사용자 대기 전에 저장한다.

### 파일과 승인 의존성

버전별 manifest에 대상·단계·시각, 실제 파일 경로/역할/SHA256, 기반 컨셉/Blender/리그 버전, 도구·스크립트·설정과 QA 증거를 둔다.
의존 텍스처와 재현에 필요한 캐시를 패킹하거나 함께 보존한다. 사용자 승인 여부는 manifest에 중복 기록하지 않고 카드의 실제 발언·대상·manifest 해시 이력을 정본으로 한다.

승인 파일/manifest는 덮어쓰지 않는다. 본제작은 승인 초안의 별도 파생 버전이며 이전 승인을 삭제할 필요가 없다.
외형을 바꾸는 새 후보는 영향받는 외형 검토를 다시 거치고, 토폴로지/리그/클립 수정은 관련 변형·동작·엔진 QA를 다시 실행한다.
파일 해시가 달라지거나 사라지면 이전 증거를 그대로 승계하지 않는다. 해시 확인은 파일 동일성의 근거이며 품질 합격의 근거는 아니다.
공유 문서는 수정 직전 다시 읽어 자기 절만 반영하고, 다른 세션 기록을 통째로 덮지 않는다.

### 재개와 구버전 이관

1. 현재 카드의 범위·이력·피드백·다음 행동을 읽고 실제 파일/manifest와 대조한다.
2. `job`의 로그·실행 시각·명령·출력으로 실제 상태를 확인한다. PID만 믿고 종료하거나 중복 실행하지 않는다.
3. `awaiting_user`이면 기존 근거로 승인이 충족됐는지 먼저 확인한다. 새 증거가 없으면 후보를 제시하고 검토를 기다린다.
4. `working`이면 마지막 편집본에서 진행한다. 장애가 해결되거나 사용자가 재개하면 같은 지점에서 이어간다.
5. v1의 `complete`는 **컨셉/초안 인계 완료**로만 해석한다. 새 전체 제작 요청이 있으면 확인한 승인을 보존하고 v2 `production`으로 옮겨 미완료 기술 단계부터 재개한다. 전체 클립/게임 QA가 없으면 전체 완료로 승격하지 않는다.
6. v2의 `complete`도 기록된 scope에 한정한다. 범위 확대 요청 없이 새 작업을 시작하지 않는다.

스킬 호출만으로 새 goal·예약·채팅·메시지를 만들지 않는다. 세션을 바꿀 때는 같은 카드의 실제 체크포인트와 실행 시작문을 제공한다.

## 납품과 완료

애니메이션 요청은 **실제 모델 동작 제작 → 정상 속도 영상 → 디코딩/화면 검수 → 사용자 제시**까지 포함한다.
카메라 턴테이블·정지 포즈·리그 존재·생성 명령 성공은 동작 완료의 증거가 아니다.
세부 납품·워터마크·인게임 증거 기준은 [공통 납품 절차](workflow.md#production-delivery)를 적용한다.

카드에 완료 클립·원본·출력·프레임 범위·QA·제시 영상·사용자 피드백을 연결한다. 편집 가능한 원본, 필요한 텍스처/캐시, 게임용 출력, 검사 증거와 재개 지점을 함께 둔다.
사용자 취향 승인과 기술 QA를 분리한다. 사용자가 좋아해도 실패한 접촉/게임 연결을 통과로 바꾸지 않는다.

`production` 완료는 요청한 모델/리그/클립 QA와 엔진 검수 범위가 충족되고 실제 결과를 제시했을 때다.
GeometryCache/LevelSequence 프리뷰만 있는데 게임 연결이 요청됐다면 `preview`로 남긴다. 도구가 없거나 해결되지 않은 중요 결함이 있으면 미완료 범위와 재개 조건을 명시한다.
컨셉/모델만 요청된 경우 해당 범위 완료와 후속 인계를 기록하며 기술 제작을 수행했다고 쓰지 않는다.

## 절차 점검 사례

| 상황 | 진행 |
|---|---|
| 소 전체 제작 요청, 외형 미정 | 소/본체/탈 구조 컨셉과 실제 3D 검토 후 짧은 시험부터 게임 검수까지 |
